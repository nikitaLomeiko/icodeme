# Технический аудит ICodeme

**Аудит завершён частично.** Я проверил основные цепочки выполнения NestJS и React: аутентификацию, API, учебные планы, профили, избранное, запуск Docker, терминал, клиентское состояние и тесты. В проекте 653 исходных файла frontend/backend; каждый компонент и вспомогательный файл вручную не проверен. Поэтому выводы ниже относятся к указанным файлам и прослеженным сценариям, а не ко всему проекту без исключения.

Диагностика TypeScript выполнена в режиме `--noEmit --incremental false` для обоих приложений: ошибок компиляции не обнаружено. Тесты не запускались, поскольку некоторые сценарии могут создавать файлы или менять внешнее состояние. Команды записи, сборки, линтеры с исправлением и обращения к Docker/MongoDB не выполнялись.

**Состояние Git на момент аудита:** начальный и итоговый `git status --porcelain=v1` совпали по списку изменённых и новых путей. Все показанные изменения, включая файлы `.next-dev`, существовали до аудита. Файлы проекта в ходе аудита не изменялись. Этот отчёт записан в файл позднее по отдельному запросу пользователя.

## CRITICAL

**Подтверждённых критических уязвимостей нет.** Запуск пользовательского кода через Docker создаёт высокий инфраструктурный риск, описанный в H-01; подтвердить выход из изоляции без запрещённого динамического испытания нельзя.

## HIGH

### H-01 — Безопасность: выполнение пользовательского кода рядом с Docker socket

**Файлы:** `docker-compose.yml:18–20`, `apps/backend/Dockerfile:32–49`, `apps/backend/src/modules/ide/services/docker.service.ts:432–467`, `apps/backend/src/modules/study/factories/test-study-module.factory.ts:169–178`.

Backend имеет доступ к `/var/run/docker.sock`, а пользовательские файлы участвуют в сборке образа. Тестовый Dockerfile устанавливает зависимости из присланного `requirements.txt`. У runtime-контейнера есть ограничения сети, памяти, процессов и capabilities, но не задан непривилегированный `User` или `ReadonlyRootfs`. Компрометация backend в такой схеме даёт доступ к управлению Docker хоста; выполнение кода при сборке повышает значение границы изоляции. **Последствие:** потенциальный выход за пределы учебного задания и воздействие на инфраструктуру при ошибке изоляции. **Рекомендация:** вынести сборку и исполнение в отдельный изолированный worker без доступа API-процесса к Docker socket, задать непривилегированного пользователя и усилить профиль изоляции сборки и запуска. **Статус:** архитектурный риск подтверждён кодом; эксплуатация требует дополнительной проверки.

### H-02 — Функциональность: созданные пользователем планы не проходят полный цикл генерации

**Файлы:** `apps/frontend/src/entities/study/api/study.api.ts:9–47`, `apps/backend/src/modules/study/controllers/study.controller.ts:73–119`, `apps/backend/src/modules/study/services/study-plan.service.ts:88–250`.

Backend предоставляет создание модулей, уровней, шагов и содержимого отдельными маршрутами. Frontend вызывает создание плана и добавление первоначального тестового модуля, но вызовов маршрутов `study/modules`, `study/levels`, `study/steps` и генерации содержимого в клиентском коде не найдено. Новый план создаётся с пустым `studyPlanJSON`. **Последствие:** пользователь может получить пустой план без пути к полноценному обучению. **Рекомендация:** связать генерацию с явным клиентским процессом и состояниями загрузки/ошибок либо выполнять её на backend при создании плана. **Статус:** подтверждено анализом кода и поиском вызовов.

### H-03 — Функциональность: сгенерированные шаги с кодом не получают параметры запуска

**Файлы:** `apps/backend/src/modules/study/services/study-plan.service.ts:160–167`, `apps/backend/src/modules/ide/services/ide-runtime.service.ts:43–54`, `apps/frontend/src/widgets/step-shell/components/code-step-view.tsx:33–48`.

При генерации каждый шаг получает `settings: {}`. Маршрут запуска требует `settings.dockerFile` и `settings.startCommand`; без них возвращается ошибка. Значения по умолчанию на frontend задают только язык и имя файла. **Последствие:** даже после ручного вызова генерации практические задания не запускаются. **Рекомендация:** назначать проверенную конфигурацию runtime по языку на сервере при создании шага, а не полагаться на данные клиента или ответ модели. **Статус:** подтверждено анализом кода.

### H-04 — Бизнес-логика: прохождение теста не сохраняет прогресс

**Файлы:** `apps/frontend/src/features/quiz/ui/results.screen.tsx:16–39`, `apps/frontend/src/features/quiz/model/store/quiz.slice.ts:67–69`, `apps/backend/src/modules/study/services/study.service.ts:197–212`, `apps/backend/src/modules/study/services/study-plan.service.ts:160–167`.

Результат вычисляется и завершается только в локальном состоянии. В проверенных контроллерах нет маршрута фиксации результата или завершения шага; сгенерированные шаги создаются с `isCompleted: false`. Методы начисления опыта и достижений профиля не вызываются из учебного процесса. **Последствие:** пройденный тест не продвигает пользователя по плану и теряется после перезагрузки. **Рекомендация:** добавить серверный сценарий сдачи с проверкой ответов, идемпотентной фиксацией завершения и атомарным обновлением прогресса. **Статус:** подтверждено анализом кода и поиском связей.

### H-05 — Производительность: поиск шага загружает все планы пользователя

**Файлы:** `apps/backend/src/modules/study/services/study.service.ts:46–63`, `apps/backend/src/modules/ide/services/ide-runtime.service.ts:34–38`.

Каждый запуск кода вызывает `repositoryStudy.find({ userId })`, который материализует все документы, после чего код обходит все модули, уровни и шаги в памяти. Индекс `Study.userId` помогает найти документы, но не устраняет их полную передачу и обход. **Последствие:** задержка и расход памяти растут с числом и размером планов; именно этот запрос стоит перед дорогим запуском контейнера. **Рекомендация:** хранить адресуемый `stepId` в отдельной коллекции либо индексировать шаги и выбирать только нужный план/элемент. **Статус:** подтверждено анализом кода.

### H-06 — Безопасность идентичности: GitHub email принимается без проверки

**Файлы:** `apps/backend/src/modules/auth/strategies/github.strategy.ts:25–32`, `apps/backend/src/modules/auth/services/oauth.service.ts:115–176`.

Стратегия берёт `emails[0].value`, не проверяя признак подтверждения; при отсутствии email синтезирует адрес `${username}@github.com`. Этот адрес становится `email` подтверждённого пользователя. Хотя код не привязывает такой OAuth-вход к уже существующему аккаунту с тем же адресом, это нарушает достоверность email и может создавать конфликты регистрации или доставки. **Рекомендация:** получать подтверждённый основной email через GitHub API; при его отсутствии хранить аккаунт без подтверждённого email и запросить отдельную проверку. **Статус:** подтверждено анализом кода; реальные ответы провайдера не проверялись.

### H-07 — Доступность: нет квоты на генерацию AI-контента для пользователя

**Файлы:** `apps/backend/src/modules/study/controllers/study.controller.ts:73–119`, `apps/backend/src/modules/study/services/study-plan.service.ts:202–250`, `apps/backend/src/modules/auth/strategies/auth-security.guard.ts:22–68`.

Глобальный rate limit охватывает только `/auth/` и `/oauth/`. Учебные маршруты вызывают платную модель без пользовательской квоты и ограничения параллельных запросов. Для содержимого шага предварительная проверка наличия результата отсутствует, и повторный вызов снова обращается к модели перед перезаписью поля. **Последствие:** один авторизованный пользователь может создать значительные расходы и нагрузку. **Рекомендация:** пользовательские лимиты, дедупликация запросов по шагу, возврат уже сохранённого результата и учёт стоимости. **Статус:** подтверждено анализом кода.

### M-02 — MongoDB: обновление профиля основано на устаревающем снимке

**Файлы:** `apps/backend/src/modules/profile/services/profile.service.ts:105–125`, `apps/backend/src/modules/profile/services/profile.service.ts:169–211`, `apps/backend/src/modules/profile/services/profile.service.ts:213–252`.

Возвращаемый объект также строится из старого снимка. **Последствие:** потерянный опыт, достижения или поля профиля. **Рекомендация:** использовать атомарные операторы MongoDB, фильтр версии документа либо транзакцию для связанных изменений. **Статус:** подтверждено анализом кода.

### M-03 — Избранное: удаление отсутствующей ссылки объявляется успешным

**Файл:** `apps/backend/src/modules/profile/services/profile-storage.service.ts:112–136`.

После `$pull` проверяется `matchedCount` документа с нужным `documentId`, а не факт удаления ссылки. Если `favoriteId` отсутствует, метод возвращает `success: true`. **Последствие:** клиент ошибочно считает операцию выполненной и может разойтись с состоянием сервера. **Рекомендация:** проверять `modifiedCount` и отдельно обрабатывать уже удалённую ссылку как явно идемпотентный случай. **Статус:** подтверждено анализом кода.

### M-04 — React: локальное избранное обновляется раньше подтверждения состояния и с замыканием на старом списке

Кнопка меняет вид сразу после вызова `addLineToFavorites`, до ответа сервера. Проверка ошибки учитывает лишь распознанный `ApiError`. **Последствие:** серверное и видимое избранное расходятся. **Рекомендация:** инвалидировать query после мутации либо вести оптимистичное обновление с откатом и функциональным обновлением состояния. **Статус:** подтверждено анализом кода.

### M-05 — React: глобальный MobX store документа переживает смену аккаунта

### M-09 — Авторизация: ответ отправки кода раскрывает существование email

Rate limit снижает скорость перебора, но не устраняет различимый ответ. **Последствие:** перечисление зарегистрированных адресов. **Рекомендация:** одинаковый публичный ответ и время обработки для обоих случаев, внутреннее логирование результата. **Статус:** подтверждено анализом кода.

### M-10 — Docker: распределённая квота контейнеров зависит от подсчёта до резервирования

**Файл:** `apps/backend/src/modules/ide/services/docker-runtime-coordinator.service.ts:96–181`.

Под глобальным lease код считает активные контейнеры и резервации, затем создаёт резервацию. После запуска резервация удаляется асинхронно. При сбое обновления/удаления или истечении lease во время долгой операции подсчёт может расходиться с фактической ёмкостью. **Последствие:** ложный отказ в запуске либо превышение настроенного лимита. **Рекомендация:** проверять владение lease при продлении и делать переход «резервация → активный runtime» согласованным; добавить метрики фактического расхождения. **Статус:** риск подтверждён анализом кода; межпроцессный сценарий не проверялся.

### M-11 — Frontend/backend: адрес API имеет опасный production fallback

**Файлы:** `apps/frontend/src/shared/api/consts/base-url.ts:1–7`, `apps/frontend/Dockerfile:22–28`.

При отсутствии `NEXT_PUBLIC_BACKEND_URL` клиент использует `http://localhost:3000/`, в том числе у внешнего посетителя. Значение из `NEXT_PUBLIC_*` встраивается при сборке; переменная, заданная только при запуске контейнера, его не исправит. **Последствие:** приложение обращается к localhost компьютера пользователя или к неподходящему HTTP API. **Рекомендация:** требовать адрес API при production build либо использовать одноимённый серверный proxy-маршрут. **Статус:** подтверждено анализом кода; фактическая конфигурация развёртывания не проверялась.

### M-12 — Тестируемость: сценарии с базой и Docker не покрыты безопасной диагностикой

**Файлы:** `apps/backend/package.json:11–24`, `apps/backend/test/docker-runtime.integration.cjs:1`, `apps/backend/test/auth-security.test.cjs:1`.

В проекте есть unit- и интеграционные тесты, но по условиям аудита они изучались без запуска. Компиляция подтверждает типы, но не транзакции MongoDB, гонки refresh token, работу Docker или браузерные сценарии. **Последствие:** перечисленные конкурентные и инфраструктурные дефекты могут проявляться только при выполнении. **Рекомендация:** в отдельном разрешённом окружении запускать тесты на временных MongoDB/Docker ресурсах и добавить проверки обнаруженных сценариев. **Статус:** ограничение диагностики подтверждено; результаты тестов неизвестны.

У функций, работающих с планом, нет ясной границы между учебной логикой и настройкой исполнения. **Последствие:** изменения runtime затрагивают формат учебных данных и усложняют миграции. **Рекомендация:** разделить метаданные плана, прогресс, контент шага и проверенную конфигурацию runtime в явные модели. **Статус:** подтверждено анализом кода.

### L-03 — Организация: фиктивные ответы теста и неиспользуемые методы проверки

**Файлы:** `apps/backend/src/modules/study/services/study-generation.service.ts:121–145`, `apps/frontend/src/features/quiz/ui/results.screen.tsx:20–29`.

`checkQuiz` и `checkCode` реализованы в сервисе, но не подключены к контроллерам; результат теста считается на клиенте по правильным ответам, которые уже переданы браузеру. **Последствие:** неясно, какие методы являются действующей бизнес-логикой; экзамен нельзя считать достоверной серверной оценкой. **Рекомендация:** определить единый сценарий проверки и убрать либо подключить неиспользуемые методы. **Статус:** подтверждено анализом кода и поиском вызовов.

### L-04 — Стиль: низкоуровневая работа с DOM внутри React-компонента

**Файл:** `apps/frontend/src/features/document/ui/components/favorite.wrapper.tsx:26–52,109–195`.

Компонент создаёт кнопки через `document.createElement`, меняет `innerHTML`, стили и цепочки `setTimeout`. Логика отображения, сетевой запрос и управление DOM смешаны в одном месте. Используемые строки `innerHTML` здесь постоянные, поэтому подтверждённой XSS через них нет. **Последствие:** сложнее поддерживать состояние кнопки, доступность и очистку обработчиков. **Рекомендация:** вынести интерактивное управление в React-компонент или отдельный хук с явной очисткой таймеров и слушателей. **Статус:** подтверждено анализом кода.

## Десять наиболее серьёзных проблем

1. H-01 — выполнение пользовательского кода при доступе backend к Docker socket.
2. H-02 — отсутствие полного клиентского процесса генерации планов.
3. H-03 — невозможность запуска сгенерированных практических шагов.
4. H-04 — отсутствие серверной фиксации прохождения тестов.
5. H-07 — отсутствие квот на AI-генерацию.
6. H-05 — полный обход планов перед запуском кода.
7. H-06 — неподтверждённый GitHub email.
8. M-01 — разрастание одного документа `Study`.
9. M-02 — потеря конкурентных обновлений профиля.
10. M-11 — fallback API на localhost посетителя.

**Порядок устранения:** сначала изоляция Docker и квоты расходов; затем полный серверный контракт учебного процесса и его подключение к frontend; после этого достоверность OAuth email и атомарность данных; далее разделение документов MongoDB, согласование API-типов и упрощение клиентского состояния.

**Риски масштабирования:** рост стоимости AI без квот, задержки и предел размера `Study`, конкуренция за Docker-ресурсы, расхождение прогресса между браузером и сервером, усложнение сопровождения нескольких независимых stores.

## Непроверенные области

Не выполнен построчный аудит всех файлов: **backend** — вспомогательные `core/helpers`, часть `core/config`, шаблоны email, данные и промпты, все ветви `docker-runtime.utils.ts`, полный набор spec/e2e; **frontend** — большинство компонентов `src/shared/ui/kit/**`, визуальные компоненты `src/entities/**/ui/**`, `src/widgets/auth-layout/**`, `src/widgets/settings-view/**`, CSS и тестовые страницы `app/test/**`; **инфраструктура** — реальная конфигурация MongoDB, Docker daemon, OAuth-провайдеров и production окружения. Эти области не включены в утверждение о проверенном коде. Причина — объём проекта и запрет на команды, которые могут менять состояние; динамические тесты, проверки контейнеров, БД, сети и браузера не проводились.
