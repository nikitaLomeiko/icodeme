**Охват:** подробно прослежены основные цепочки авторизации, профиля, учебного плана, тестов, запуска кода и соответствующие вызовы frontend. Выводы ниже относятся к прочитанному текущему коду, включая незакоммиченные пользовательские изменения. Прежние отчёты в репозитории не принимались за доказательство.

## CRITICAL

Подтверждённых критических ошибок, для которых по одному лишь коду можно обоснованно утверждать немедленную компрометацию системы, не найдено. Риск доступа backend к Docker socket описан ниже как HIGH: его итоговая тяжесть зависит от изоляции сервера и конфигурации Docker.

## HIGH

### H-01 — Правильные ответы тестов раскрываются до отправки результата

- **Категория:** безопасность бизнес-логики; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study.service.ts:99`, `apps/backend/src/modules/study/services/study-plan.service.ts:223`, `apps/frontend/src/widgets/step-shell/lib/utils/adapt-study-quiz.ts:15`.
- **Проблема:** `GET /study/me/:studyId` возвращает тест вместе с `variants.isTrue`, `truefolse.correct`, `inputs.correct` и `code.correctCode/correctResult`. Клиент преобразует эти поля в `correct`. Тот же пользователь затем отправляет ответы в `submitQuiz`.
- **Почему это неверно:** сервер проверяет знание по секрету, который уже передал проверяемому клиенту. Через сетевой ответ можно составить запрос с результатом 100% без прохождения интерфейса.
- **Последствия:** недостоверный прогресс и любые будущие достижения, основанные на завершении шага.
- **Рекомендация:** выдавать отдельную публичную модель вопроса без правильных ответов; эталон хранить только на сервере. Для показа разбора после попытки предусмотреть отдельный ответ с правилами доступа.

### H-02 — Сервер не ограничивает попытки и время прохождения теста

- **Категория:** проверка прогресса; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study-plan.service.ts:223`, `apps/frontend/src/features/quiz/ui/components/timer.provider.tsx:24`.
- **Проблема:** таймер и пропуск просроченного вопроса действуют только в React. `submitQuiz` не проверяет время начала, срок ответа или число попыток.
- **Почему это неверно:** клиентские ограничения обходятся прямым вызовом API или изменением состояния браузера.
- **Последствия:** обход правил экзамена; при многократных запросах возможна дополнительная нагрузка.
- **Рекомендация:** хранить попытку и сроки на сервере, проверять их атомарно при отправке, определить лимит повторов. Клиентский таймер оставить средством отображения.

### H-03 — Проверка вопроса с кодом сводится к сравнению строк

- **Категория:** бизнес-логика тестирования; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study-plan.service.ts:292`, `apps/backend/src/modules/study/models/quiz.types.ts:28`.
- **Проблема:** ответ типа `code` считается верным, если нормализованная строка совпала с одним `correctCode` **или** `correctResult`. Код не выполняется и не проверяется на тестовых случаях.
- **Почему это неверно:** иной корректный алгоритм отклоняется; строка ожидаемого вывода принимается вместо решения.
- **Последствия:** ложные положительные и отрицательные результаты, непредсказуемый опыт учащегося.
- **Рекомендация:** разделить вопросы «каков вывод» и «напишите код». Для второго типа запускать код в изолированной среде с серверными тестами и лимитами.

### H-04 — Backend с пользовательским кодом имеет доступ к Docker socket хоста

- **Категория:** изоляция инфраструктуры; **статус:** подтверждено анализом конфигурации, итоговый риск требует проверки окружения.
- **Место:** `docker-compose.yml:18`, `apps/backend/src/modules/ide/services/docker.service.ts:93`.
- **Проблема:** `/var/run/docker.sock` подключён к backend, который принимает проекты пользователей и управляет сборкой и запуском контейнеров. Для контейнера запуска заданы полезные ограничения, но сам backend обладает доступом к Docker daemon.
- **Почему это риск:** компрометация backend или ошибка в обработке проекта открывает путь к управлению контейнерами хоста; ограничения `HostConfig` пользовательского контейнера не ограничивают полномочия backend.
- **Последствия:** потенциальный выход за границы приложения вплоть до контроля хоста, в зависимости от развёртывания.
- **Рекомендация:** вынести выполнение в отдельный узел с минимальными правами и изолированным Docker daemon; ограничить API посредником и квотами. Проверить фактические права socket и модель угроз deployment.

### H-05 — Сборка образа не имеет жёсткого срока завершения

- **Категория:** доступность, Docker; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/ide/services/docker-image.service.ts:98`, `apps/backend/src/modules/ide/services/docker-runtime-coordinator.service.ts:69`, `apps/backend/src/modules/ide/services/docker.service.ts:196`.
- **Проблема:** ожидание свободного слота ограничено, а сама `docker.buildImage` и поток `followProgress` не имеют deadline или отмены. Лимит времени шага начинает действовать только после создания контейнера.
- **Почему это неверно:** зависшая сборка удерживает слот и резервирование без гарантированного освобождения.
- **Последствия:** исчерпание слотов сборки, задержки других пользователей, рост диска при неудачных сборках.
- **Рекомендация:** задавать общий deadline сборки, прерывать поток и операцию Docker, освобождать слот и убирать промежуточные артефакты при истечении срока.

### H-06 — Параллельная генерация одного содержимого повторно тратит квоту и перезаписывает результат

- **Категория:** конкурентность, стоимость ИИ; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study-plan.service.ts:343`, `apps/backend/src/modules/study/services/study.service.ts:242`.
- **Проблема:** два запроса читают пустой шаг, оба вызывают `quota.consume`, оба обращаются к ИИ; затем оба выполняют `$set` в одном документе `studyStepContent`. Последний ответ побеждает.
- **Почему это неверно:** проверка существования и запись не составляют одну операцию, нет блокировки по ключу содержимого.
- **Последствия:** двойные затраты и расход квоты, разные ответы пользователям при одном сохранённом результате.
- **Рекомендация:** резервировать ключ генерации атомарно, возвращать текущую задачу повторным запросам; сохранять результат условным обновлением и возвращать фактически сохранённое значение.

### H-07 — Старые шаги без `id` нельзя дополнить генерируемым содержимым

- **Категория:** совместимость данных; **статус:** подтверждено анализом кода; наличие таких записей в базе не проверено.
- **Место:** `apps/backend/src/modules/study/services/study.service.ts:79`, `apps/backend/src/modules/study/services/study.service.ts:257`.
- **Проблема:** при чтении `withStepIds` создаёт отсутствующий `id` только в возвращаемой копии плана. `setStepContent` повторно читает исходный документ и возвращает `false`, если `step.id` отсутствует.
- **Почему это неверно:** ответ API выглядит исправленным, но сохранённая запись остаётся несовместимой с операцией записи.
- **Последствия:** генерация документации, задания или теста для старого шага завершается 404 после вызова ИИ и расхода квоты.
- **Рекомендация:** мигрировать сохранённые шаги или атомарно закреплять `id` в базе до генерации.

## MEDIUM

### M-01 — Резервное создание и удаление профиля теряют атомарность

- **Категория:** MongoDB, согласованность; **статус:** подтверждено анализом кода; применимость зависит от режима MongoDB.
- **Место:** `apps/backend/src/modules/profile/services/profile.service.ts:70`, `apps/backend/src/modules/profile/services/profile.service.ts:129`.
- **Проблема:** при неподдерживаемых транзакциях профиль и его хранилище создаются или удаляются отдельными операциями. Вызов `initialize` способен восстановить хранилище при повторном создании, но сбой между операциями всё равно оставляет частичное состояние.
- **Последствия:** профиль без хранилища или осиротевшее хранилище до следующего восстановления.
- **Рекомендация:** использовать MongoDB с транзакциями либо оформить резервный путь как идемпотентный процесс с явным восстановлением и проверкой результата каждого шага.

### M-02 — Список учебных планов загружает полные вложенные документы

- **Категория:** производительность, API-контракт; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study.service.ts:32`, `apps/frontend/src/entities/study/api/study.api.ts:25`.
- **Проблема:** `GET /study/me` читает все планы пользователя с полным `studyPlanJSON`, хотя список и навигация используют главным образом метаданные. Проекции и пагинации нет.
- **Последствия:** рост времени ответа, трафика и памяти браузера по мере накопления планов; повторные загрузки больших данных.
- **Рекомендация:** создать облегчённый DTO списка и отдельный запрос деталей, добавить пагинацию или предел числа планов в ответе.

### M-03 — У избранного нет ограничения общего размера документа

- **Категория:** MongoDB, валидация; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/profile/dto/favorite.dto.ts:10`, `apps/backend/src/modules/profile/services/profile-storage.service.ts:66`.
- **Проблема:** длина одной записи ограничена, но количество документов и ссылок в `favorites` не ограничено. Всё избранное пользователя хранится в одном документе MongoDB.
- **Последствия:** увеличение стоимости чтения и обновления; достижение лимита BSON и прекращение добавления закладок.
- **Рекомендация:** хранить записи избранного отдельными документами с составным уникальным индексом либо установить и проверять явные квоты.

### M-04 — DTO отправки ответов проверяет только верхний уровень

- **Категория:** API-контракт, валидация; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/dto/study.dto.ts:41`, `apps/backend/src/modules/study/services/study-plan.service.ts:239`.
- **Проблема:** `@IsObject()` подтверждает лишь объект `answers`. Схема ключей, длина строк, размеры массивов и соответствие идентификаторам вопросов не валидируются декларативно; сервис проверяет тип только у отдельных используемых значений.
- **Последствия:** непредсказуемый контракт, лишняя обработка некорректных данных и сложность развития проверки.
- **Рекомендация:** ввести явный DTO попытки или отдельную функцию валидации с ограничением количества и длины ответов, проверять принадлежность ключей текущему тесту.

### M-05 — После ошибки сохранения теста нет повторной отправки той же попытки

- **Категория:** React, восстановление после ошибок; **статус:** подтверждено анализом кода.
- **Место:** `apps/frontend/src/widgets/step-shell/components/quiz-completion.tsx:13`.
- **Проблема:** `submitted.current` устанавливается до получения результата. При сетевой ошибке компонент сообщает о необходимости обновить страницу и пройти тест заново; повторно отправить уже собранные ответы нельзя.
- **Последствия:** потеря результата при кратковременном сбое сети.
- **Рекомендация:** хранить состояние `idle/submitting/saved/error`, предоставить повторную отправку той же попытки; серверную операцию сделать идемпотентной.

### M-06 — Контракт ответов генерации частично заменён на `unknown`

- **Категория:** типизация frontend/backend; **статус:** подтверждено анализом кода.
- **Место:** `apps/frontend/src/entities/study/api/study.api.ts:64`, `apps/backend/src/modules/study/services/study-plan.service.ts:115`.
- **Проблема:** результаты генерации уровней, шагов и тестов на frontend объявлены как `IResponse<unknown>`, хотя backend возвращает конкретные структуры.
- **Последствия:** ошибки контракта обнаруживаются позже, преобразования и UI зависят от непроверенных предположений.
- **Рекомендация:** определить типы ответов для каждого endpoint и проверять внешние данные на границе API; по возможности генерировать типы из общей схемы.

### M-07 — Проверка языка среды основана на поиске слов в произвольном описании

- **Категория:** проектирование, бизнес-логика; **статус:** подтверждено анализом кода.
- **Место:** `apps/backend/src/modules/study/services/study-runtime-config.ts:33`, `apps/backend/src/modules/study/services/study-plan.service.ts:170`.
- **Проблема:** выбор Python или JavaScript выполняется регулярными выражениями по `study.context`, который может быть свободным текстом до 4000 символов.
- **Последствия:** неверный runtime для неоднозначного описания; отказ в генерации шагов с кодом, если язык написан иначе.
- **Рекомендация:** хранить канонический идентификатор языка отдельно от текстовой цели обучения и проверять его при создании плана.

### M-08 — Результат frontend и серверный статус теста имеют разные источники истины

- **Категория:** взаимодействие frontend/backend; **статус:** подтверждено анализом кода.
- **Место:** `apps/frontend/src/features/quiz/model/libs/utils/scoring.ts:43`, `apps/frontend/src/features/quiz/ui/results.screen.tsx:204`, `apps/frontend/src/widgets/step-shell/components/quiz-completion.tsx:50`.
- **Проблема:** экран результатов рассчитывает правильность локально, а сохранение прогресса выполняется отдельной серверной проверкой. При изменении правил или данных эти оценки могут разойтись.
- **Последствия:** пользователь видит результат, который не соответствует сохранённому прогрессу.
- **Рекомендация:** возвращать серверный разбор попытки и использовать его как источник итогового результата для учебного теста.

## LOW

### L-01 — Логика избранного напрямую управляет DOM и множеством таймеров

- **Категория:** читаемость, React; **статус:** подтверждено анализом кода.
- **Место:** `apps/frontend/src/features/document/ui/components/favorite.wrapper.tsx:26`.
- **Проблема:** компонент вручную создаёт кнопки и индикаторы, меняет inline-стили, назначает обработчики и вложенные `setTimeout`. Состояние кнопки отдельно от React и MobX.
- **Последствия:** код трудно сопровождать; при перерисовке документа и смене избранного возможны кратковременные несогласованности. Таймеры индикатора не очищаются при размонтировании.
- **Рекомендация:** вынести интерактивность в React-компонент строки документа либо в небольшой хук с явной очисткой обработчиков и таймеров.

### L-02 — Глобальный store избранного удаляет первый `span` внутри произвольного элемента

- **Категория:** корректность DOM; **статус:** подтверждено анализом кода.

- **Последствия:** при удалении закладки может исчезнуть часть оформления или содержимого документа.
- **Рекомендация:** хранить ссылку на собственный индикатор либо искать элемент по специальному атрибуту.

### L-03 — Диагностический вывод остаётся в пользовательских путях

- **Рекомендация:** убрать вывод либо включать его только через управляемый режим диагностики.

### L-04 — Ручной парсер PDF-документации слишком велик для одной функции ответственности

- **Категория:** читаемость, поддерживаемость; **статус:** подтверждено анализом структуры файла.

- **Последствия:** различия между экспортами и высокая стоимость исправления ошибок парсинга.
- **Рекомендация:** разбирать Markdown один раз в общую промежуточную структуру и разделить преобразование блоков и рендеринг PDF.

## Десять наиболее серьёзных проблем

1. H-04 — полномочия backend через Docker socket.
2. H-01 — раскрытие правильных ответов теста.
3. H-02 — отсутствие серверных ограничений попыток и времени.
4. H-05 — отсутствие deadline сборки образа.
5. H-06 — параллельная генерация одного содержимого.
6. H-03 — строковая проверка заданий с кодом.
7. H-07 — невозможность дополнить старые шаги без `id`.
8. M-01 — неатомарный резервный путь работы с профилем.
9. M-03 — неограниченный рост избранного в одном документе.
10. M-02 — выдача полных планов в списке.

## Рекомендуемый порядок устранения

1. Определить модель угроз Docker и изолировать службу выполнения кода; добавить deadline сборки.
2. Разделить публичные вопросы и серверные эталоны, затем ввести серверную модель попытки и времени.
3. Исправить семантику проверки кода и сделать серверный результат источником истины для UI.
4. Сделать генерацию содержимого идемпотентной; мигрировать шаги без `id`.
5. Разделить DTO списка и деталей плана, ограничить рост данных избранного.
6. Закрыть разрывы типизации API и упростить наиболее сложные UI-модули.

## Риски при масштабировании

Главные риски — исчерпание Docker-слотов зависшими сборками, рост объёма ответов учебных планов и документов MongoDB, повторная оплата параллельных ИИ-запросов, а также зависимость безопасности всей платформы от изоляции backend с Docker socket. При увеличении числа пользователей локальные результаты тестов и серверный прогресс также будут чаще расходиться из-за сетевых ошибок и повторных попыток.

## Непроверенные области

Аудит **не завершён для всего проекта**. Помимо указанных выше файлов, точечно прочитанных конфигураций и изученных маршрутов, индивидуальный построчный анализ не проводился для следующих групп файлов:

- `apps/frontend/src/shared/ui/**` — основная масса UI-компонентов, включая редактор, карусель, модальные окна и оформление; изучены только перечисленные в замечаниях файлы и несколько связанных компонентов.
- `apps/frontend/src/features/**` — остальные формы авторизации и профиля, настройки, карты и компоненты теста за пределами рассмотренных потоков.
- `apps/frontend/src/entities/**` и `apps/frontend/src/widgets/**` — оставшиеся модели, селекторы, UI-компоненты и вспомогательные функции.
- `apps/frontend/src/pages-root/**`, `apps/frontend/app/**` — большинство страниц и маршрутов Next.js.
- `apps/backend/src/core/**` — часть низкоуровневых хранилищ, настроек и AI-провайдера.
- `apps/backend/src/modules/ide/**`, `auth/**`, `profile/**`, `study/**` — оставшиеся вспомогательные классы, шаблоны, фабрики и тестовые файлы; основные контроллеры и сервисные цепочки прочитаны.
- Существующие `*.spec.ts`, `*.test.cjs`, документация, lock-файлы и содержимое `data/prompts` не прошли полный аудит.

Причина ограничения: объём проекта — 659 исходных файлов, а безопасный запуск тестов и проверка реальной MongoDB/Docker-инфраструктуры в рамках режима только чтения не проводились. Поэтому отсутствие замечания по перечисленным областям **не означает отсутствие проблемы**.
